# 01 软硬件划分：模型纠正"MQTT 放 PL、DP 接 PL"的设想

会话：三层架构（MQTT 消息、CNN 推理、Mini DP 着色显示）方案与实现　日期：2026-11-01

## 提示词（整理）
> 宏观设计是 FPGA 做三个层次：MQTT 物联网消息聚合、CNN 模型推理、Mini DP 屏幕输出模型着色。三侧要相互配合、时序收敛、高效快速。看一下整体方案，动手写代码并测试，暂时不要烧录。
> （之后）相机和 CNN 当然得一起跑，不然哪来的输入？"板上 Linux 的显示驱动支持 live 输入"是什么意思？

## 模型回答（摘要）
- 先纠正两处分层：MQTT 走 TCP，网口和 TCP/IP 协议栈在 PS 的 Linux 上，所以 MQTT 在 PS 跑，PL 只通过寄存器交出结果；Mini DP 口属于 PS 的 DisplayPort 控制器，PL 只能经它的 live 输入送画面。
- 数据流：相机 → VDMA 写内存 → PS 预处理 → PL CNN（DMA 送入）→ 结果同时写叠加层寄存器和发 MQTT。
- CNN 核改为 2 帧输入、9 路输出；`mqtt_lite.py` 只用标准库，板端代码全部按板上 Python 3.6 可解析。
- 采集、推理、MQTT 互不阻塞：采集只留最新帧，断网时先丢不重要消息，QoS 1 消息重连后补发。

## 纠错
- 第一版只给了推理 + 显示的比特流，相机设计单独存在，一次只能加载一个，用户指出"相机和 CNN 必须一起跑"。模型把板上正在用的相机设计（与板上 `fz3b_cam.bin` 来源核对过）原样复制为顶层，CNN 和显示放进同一块设计，相机寄存器地址不变，采集程序一行不改。
- 对"live 输入"模型查了板上内核（4.14，Xilinx 2018.3）：live 只有内核内部接口，没有用户态开关，"图形层用 live"的代码有 bug 会把该层关掉。于是改为整幅画面由 PL 合成，送进 DP 控制器的视频层，Linux 不碰视频层。
- 测试中抓到一个真 bug：恰好在断线瞬间发出的 MQTT 消息会丢，已修复。原 `frame_server.py` 有两处 Python 3.8 写法，在板上会跑不起来，已替换。

## 结果
- 推理仿真（Verilator 与 xsim）与 Python 参考模型逐位一致 144/144，每帧 0.565 ms。
- 合并工程三个时钟域全部收敛（见 04），资源逻辑 22%、DSP 31%、块 RAM 21%。
- 后续用户提出把标定串口接到 FPGA，模型给出反对意见：参考温度经上位机从采集服务接口取，再通过 MQTT 主题 `cmd/calibrate` 下发，不需要接串口，也不会与采集程序抢串口。
