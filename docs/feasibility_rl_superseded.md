# FPGA 实时 RL 能效控制系统 · 可行性分析

> **已被 [方案对比_散斑vsRL.md](方案对比_散斑vsRL.md) 取代**：冷却 RL 上 FPGA 无刚需，主线改为散斑 + FPGA。

> 依据：AMD 2026 FPGA 赛道选题指南；loulinux `~/Project/RL/server/happo_marl`、`phm_v41_revision`；macmini `~/WiseStars/RL/HPM论文/paper_hpm.md`（PHM 2026）。
> 训练进程（joint_v152）未触碰。

## 1. 结论

**可行，工作量中等（2 人约 6–8 周可出完整作品）。** 需要调整两点，否则评委会追问：

1. **不做 FPGA 上训练**，只做推理 + 安全逻辑。"Real-Time RL" 容易被理解为在线训练，建议改题为
   *FPGA-Based Hardware-in-the-Loop Safe RL Controller for Liquid-Cooled AI Computing Centers*。
2. **"为什么要用 FPGA" 不能靠加速 MLP 来回答**（控制周期 60 s，CPU 算 64×64 MLP 只要微秒级）。
   卖点应放在：**硬件级确定性安全联锁 + 低功耗边缘控制器 + HIL 闭环验证**。这正好对上 PHM 论文 Limitations 里写的 "Hardware-in-the-loop … remain necessary"。

## 3. 代码可部署性

| 组件 | 现状（代码） | 上 FPGA？ | 说明 |
|---|---|---|---|
| L2 策略网络 | `networks.py`：MLP obs→64→64→(2 Tanh + 3)，obs = plant_obs + 30 | ✅ 容易 | 约 8k 参数；`ap_fixed<16,6>` 量化，HLS 串行实现约数 k LUT + 几个 DSP，XC7Z020 余量很大 |
| Tier-1′ 阀门规则 | `alloc_net.py::rule_residual`：柜内去均值、dT/dt EMA、sigmoid 门、clip | ✅ 容易 | 纯定点算术，sigmoid 用查表；恒等闸门 7.729572 可直接作为硬件正确性金标准 |
| 安全联锁 / 动作屏蔽 | `phm_v41_revision/control.py`：量程 39.0–41.5 °C、测量网格、0.5 °C 限速、超时保持 | ✅ **核心亮点** | 用 RTL 状态机实现；通信超时看门狗 → 回退 G36/保持上次值 |
| L1 G36 trim-and-respond | 规则逻辑 | ⚪ 可选 | 放 PS 或 PL 都行，时间不够就放 PC |
| FMU 被控对象 | `LC_Frontier_5Cabinet.fmu`，仅 win64/linux64 二进制，23k 变量，15 s 积分 | ❌ | 无 ARM 版本，必须留在 PC |
| L3 LLM（Qwen-max） | 云 API + JSON 校验 | ❌ | 留 PC，可作为可选演示；其 JSON schema 校验结果以寄存器方式交给 PL 联锁复核 |
| PPO 训练 | GPU | ❌ | 用已冻结 checkpoint |

**注意**：HANDOFF/`L2_RESIDUAL_CLOSEOUT.md` 显示 L2 残差相对规则层增益有限（约 2–3 %，seed 敏感），而 tier-1′ 规则相对 G36 的 degree-hours 降 40 %。比赛展示应以"规则 + 冻结 RL + 硬件联锁"整体为主，不要把 RL 增益当主指标，也不要依赖正在跑的迭代。

## 4. 系统架构

```
PC (x86)                                  PYNQ-Z2
┌──────────────────────────┐   UDP/TCP   ┌──────────── PS (A9, Python) ────────────┐
│ FMU 仿真 (fmpy, 15 s)     │ ─obs帧────▶ │ 收包 → AXI-Lite/DMA 写入                 │
│ 场景/负载/天气输入         │ ◀─action─── │ 读出 action + 联锁状态 → 回包             │
│ L3 LLM (可选)             │             └──────────────┬───────────────────────────┘
│ 日志/对比/功耗记录          │                            │ AXI
└──────────────────────────┘             ┌──────────── PL ──────────────────────────┐
                                         │ ① 定点 MLP 推理 (HLS)                      │
                                         │ ② tier-1′ 规则核 (HLS)                     │
                                         │ ③ 安全联锁 FSM：量程/限速/网格/看门狗 (RTL) │
                                         │ ④ 周期计数、延迟/违规计数寄存器             │
                                         └──────────────────────────────────────────┘
```

通信协议：定长二进制帧（seq, timestamp, obs[N], CRC）；超时 → PL 看门狗自动保持/回退，不依赖 PS 软件。

## 6. 主要风险

| 风险 | 应对 |
|---|---|
| 评委质疑"FPGA 没必要" | 主打硬件联锁（软件崩溃/通信中断仍安全）、功耗、确定性延迟，用故障注入数据说话 |
| 定点化后闭环指标偏移 | 以恒等闸门 7.729572 与浮点 rollout 做逐步比对，给出误差表 |
| 与 PHM 论文内容重叠 | 报告里引用论文，比赛贡献明确为"硬件实现 + HIL"，与论文 Limitations 衔接 |
| FMU/LC-Opt 许可证 | 开源前核对 LC-Opt 上游 License，FMU 可用下载脚本代替直接分发 |
| 队员年级 | 全员须为大一至大三，否则整队划入高级组 |

## 8. 创新点升级：FPGA 预测式安全屏蔽（推荐作为主创新）

仅"MLP 推理 + 静态联锁"硬件难度偏低、创新弱。升级为：

**PL 内实现冷却系统代理模型，对每个候选动作并行做多步前瞻，选出预测安全的动作再下发。**

```
候选动作 K 个（RL 输出 / 规则输出 / 保持 / 若干扰动）
        × 负载/湿球不确定性样本 M 个
        × 前瞻 H 步
  ──▶ PL 并行代理模型 rollout ──▶ 预测最高温 / 越限度时 / 能耗
  ──▶ 硬件选择器：安全约束内能耗最小者；全部不安全 → 回退 G36
```

| 项 | 内容 |
|---|---|
| 与论文区别 | 论文联锁只查量程/限速（静态），事后靠效果带回滚；这里改为**事前预测**，且在独立硬件中执行 |
| 为什么需要 FPGA | 计算量 K×M×H 随规模线性增长（真实中心数百柜）；PL 流水线并行、延迟确定、功耗几 W、与主机软件隔离（功能安全的"多样性冗余"） |
| 代理模型 | 用现有 FMU rollout 数据拟合：线性状态空间（约 20 维）或小 MLP；定点化 |
| 硬件工作 | HLS 流水线 + 数组分割并行、定点精度设计、AXI Stream/DMA、时序收敛、资源-吞吐权衡 |
| 可测指标 | 代理模型误差；每决策 K×M×H 吞吐、延迟 P99；vs ARM A9 / x86 的加速比与每决策能耗；故障注入下越限度时减少量 |

诚实的边界：服务器 CPU 也能算完，卖点是**确定性延迟 + 低功耗 + 硬件隔离的安全冗余 + 可扩展到大规模柜数**，不是"CPU 算不动"。

工作量增加约 4 人周（代理模型 1.5、并行 HLS 核 2、实验 0.5），总计约 12 人周。§7 规划中 P1–P3 作为保底，P3 之后接入该模块。

**可选实物扩展**：小型水冷台架（加热电阻模拟机柜、水泵、散热风扇、温度传感器），FPGA 负责 PWM/转速计数/ADC 采样/联锁。演示效果强，但 FMU 训练的策略无法直接迁移，只建议用于演示安全联锁。
