# 提示词工作流

与大模型编程助手协作时反复用到、能稳定完成任务的提示词模板。尖括号里的内容按自己的题目替换，其余照抄。
每个模板后面写了本作品里的用法和效果，以及不该用它的情形。

---

## P1. 从算法描述推导软硬件划分

```
下面是一个要放到 <器件型号，例如 xczu3eg> 上实时运行的算法，每 <周期> 处理一次 <输入尺寸>。
<算法步骤，按顺序列出，每步写清输入输出的形状和数据类型>

请逐步给出：
1. 每一步的运算量（乘加次数）和数据量（字节），用表格列出，并写出计算过程；
2. 每一步放在 PS 还是 PL，依据只能是：运算量、数据量、是否需要逐位可复现、
   实现和修改成本；不要用"FPGA 更快"这类没有数字的理由；
3. PS 与 PL 之间的接口：传什么、多大、多频繁，用 AXI-Lite 还是 AXI DMA；
4. 你不确定的数字单独列出来，写清需要我在板上测什么才能确定。
不要写代码。
```

- 本作品：4 层卷积约 262 万次乘加，占全部乘加的 99.9%（FC 只有 1168 次），进 PL；预处理逻辑多变且要与训练侧逐位一致，留 PS。板上实测 PS 预处理 2 s/帧，是现在的瓶颈，这类数字只能上板测，所以模板要求助手把它列为待测项。
- 效果：要求"列出计算过程"和"不确定项单列"后，助手不再给出无依据的加速比。
- 不适用：算法本身还没定，先做算法验证再划分。

## P2. 根据综合 / 实现报告定位瓶颈

```
这是 Vivado <版本> 对 <顶层名> 的报告：
<粘贴 timing_summary.rpt 的 Design Timing Summary 和最差 10 条路径；
 utilization_hier.rpt 中占用前 10 的层级>

请回答：
1. 时序是否满足，最差路径的起点、终点、逻辑级数、走线延迟占比；
2. 哪个层级占用的 <LUT/BRAM/DSP> 与它的功能不相称（给出你预期的数量和计算方法）；
3. 针对第 1、2 条各给出一个最小修改，并说明怎样验证修改有效（看报告里哪一行）。
只依据报告里出现的数字，报告里没有的信息就说没有。
```

- 本作品：用它定位到偏置 ROM 按 8 位计数器推成 8192 深、每路占一块 BRAM（总量一度 139/140），按实际深度声明地址位宽后恢复正常（`skill/README.md` 第 2 项）。
- 配套脚本：`skill/scripts/check_vivado_reports.py` 先把报告转成指标表，粘贴给模型更短、也不会抄错数字。
- 不适用：综合阶段报告（未布线）里的时序只作参考，不要据此做时序结论。

## P3. 让助手先复现再修改（调试板上故障）

```
现象：<原样粘贴报错、dmesg、寄存器读数>
环境：<内核版本、Python 版本、相关驱动文件路径>

先不要改代码。请：
1. 列出可能原因，按可能性排序，每条写出能区分它的一个最小实验（一条命令或几行代码）；
2. 我跑完实验把输出贴给你后，再只针对被证实的原因修改；
3. 修改后给出回归测试：在没有板卡的机器上也能跑的那部分。
```

- 本作品：DMA 读结果 SIGBUS（`/dev/mem` 非对齐访问）和 MM2S 停住（重复软复位）都按这个流程定位，修复后写进 `sim/host/test_node.py` 回归。
- 效果：避免助手在原因未确认时连改多处，引入新问题。

## P4. 评估结论前的数据泄漏自查

```
下面是我的训练 / 评估划分和得到的指标：<划分方式、每段数据的采集时间和标签、指标>
请检查：
1. 训练集和测试集是否有时间上相邻、同一次采集或同一标定的数据；
2. 门限、归一化参数、超参数是否用到了测试数据；
3. 如果有，给出一个只用训练折确定这些参数的嵌套评估方案，并估计指标会怎样变化。
```

- 本作品：发现训练集混入了对照段，留出评估的指标因此虚高；改为每折留出 1 段对照、门限只用训练折的对照确定（`src/model/win_alarm/nested.py`）。
- 不适用：数据只有一段时，先补采集，评估方案救不了。
